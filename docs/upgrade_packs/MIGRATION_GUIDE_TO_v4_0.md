# MIGRATION_GUIDE_TO_v4_0.md

## 1. 목적

이 문서는 기존 2.x 또는 3.x 구조에서
v4.0 아키텍처로 이동하기 위한 마이그레이션 가이드다.

v4.0의 핵심 목표는 다음과 같다.

- 정책과 디자인 기준을 문서로 고정
- 판단을 사람 기억이 아닌 시스템으로 이전
- PR 단계에서 자동 검증이 이루어지게 함
- “왜 이 결정이 내려졌는지”를 추적 가능하게 만듦

v4.0은 운영 자동화가 아니라
“기준과 게이트를 확립하는 버전”이다.

---

## 2. v4.0의 핵심 개념 변화

### 이전(2.x / 3.x)
- 규칙이 암묵적
- 리뷰어마다 기준이 달라짐
- 실패 원인을 나중에 추적하기 어려움
- 문서보다 대화와 기억에 의존

### v4.0
- 모든 기준은 문서로 고정
- 정책 위반은 자동 검출
- PASS/FAIL의 근거가 리포트로 남음
- 결정은 로그로 추적 가능

---

## 3. v4.0에서 반드시 존재해야 하는 파일

아래는 v4.0의 “최소 구성”이다.

### 기준 문서 (필수)
- DESIGN_SYSTEM.md
- POLICY_RULES.md
- SECURITY_POLICY_RULES.md

### 디자인 자산 (필수)
- DESIGN_TOKENS.json

### 결정 추적 (필수)
- DECISION_LOG.md
- tools/ledger/log_decision.py

### 결과 저장소 (필수)
- .orchestrator/ 디렉토리

---

## 4. 기존 구조에서 유지 / 폐기 기준

### 그대로 유지해도 되는 것
- 기존 PRD / TRD / DESIGN 문서
- 기존 테스트 코드
- 기존 빌드 파이프라인

### v4.0에서 의미가 약해지는 것
- 암묵적 규칙 문서
- 리뷰 가이드만 있고 자동 검증이 없는 문서
- 사람 이름이 기준인 문서

### 제거 또는 통합 권장
- “README에만 적힌 디자인 규칙”
- CI 없이 수동으로만 확인하는 체크리스트

---

## 5. v4.0 도입 절차 (권장 순서)

### Step 1. 기준 문서 고정
다음 파일을 먼저 작성하거나 확정한다.

- DESIGN_SYSTEM.md
- POLICY_RULES.md
- SECURITY_POLICY_RULES.md

이 단계에서 중요한 점:
- 애매한 표현 금지
- 허용 / 금지 / 예외 조건을 명확히 작성

---

### Step 2. 디자인 토큰 단일화
DESIGN_TOKENS.json을
“유일한 디자인 진실의 원천”으로 설정한다.

- 색상
- 타이포그래피
- spacing
- radius
- shadow

코드 하드코딩은 이후 단계에서 정책 위반으로 간주된다.

---

### Step 3. Decision Ledger 연결
결정 로그를 남길 수 있도록
DECISION_LOG.md와 log_decision.py를 연결한다.

이 시점부터:
- 중요한 변경
- 정책 변경
- 기준 확정

은 반드시 로그로 남긴다.

---

### Step 4. CI 게이트 연결
PR 시 자동으로 다음이 수행되도록 한다.

- 디자인 정책 검사
- 보안 정책 검사
- 결과 리포트 생성
- FAIL 시 PR 차단

v4.0에서는
“자동 수정”보다 “자동 차단”이 우선이다.

---

## 6. v4.0에서의 PR 흐름

1. 개발자가 PR 생성
2. CI가 자동으로 정책 검사 실행
3. 결과 리포트 생성
4. PASS면 merge 가능
5. FAIL이면 기준 문서를 수정하거나 코드 수정

이 시점부터
“리뷰어 감정”은 기준이 아니다.
기준은 문서와 정책이다.

---

## 7. 흔한 마이그레이션 실패 패턴

- 기존 문서를 그대로 두고 v4.0을 얹으려 함
- 정책 문서가 모호한 상태로 자동화를 먼저 붙임
- DECISION_LOG를 수동 메모처럼 사용함
- CI를 선택 사항으로 둠

---

## 8. v4.0 마이그레이션 완료 체크리스트

다음이 충족되면 v4.0 마이그레이션 완료다.

- DESIGN_SYSTEM.md가 실제 기준으로 작동
- DESIGN_TOKENS.json 외 하드코딩이 정책 위반으로 감지됨
- PR에서 정책 FAIL이 자동으로 발생
- .orchestrator에 리포트가 쌓임
- DECISION_LOG.md가 append-only로 증가

---

## 9. v4.0의 한계와 다음 단계

v4.0은 “기준 확립”까지 담당한다.

다음은 포함하지 않는다.
- 변경 요청 관리
- 사고(Incident) 관리
- 예외 만료 관리
- PR 요약 코멘트
- 운영 자동화

이 영역은 v4.1에서 다룬다.

---

## 10. 최종 요약

v4.0 마이그레이션의 본질은
기능 추가가 아니다.

기준을 고정하고
판단을 시스템으로 옮기는 것이다.

이 단계가 끝나야
운영 자동화(v4.1)가 의미를 갖는다.
